# Развёртывание виртуальной машины в Proxmox через Terraform

Цель задания — подключить Terraform к Proxmox и создать ВМ с заданными
именем, CPU, RAM, диском и сетью. Стенд содержит одну ВМ Yandex Cloud
с Proxmox VE и одну гостевую ВМ Debian. Cloud-init подготавливает гостевую ОС.

## Устройство стенда

```text
Оператор ── SSH 22 / HTTPS 8006 ── ВМ YC: Debian 13 + Proxmox VE 9
                                            │
                                 vmbr10 / NAT / приватная сеть
                                            │
                                     dz10-guest: Debian 13
```

| Параметр | Узел Proxmox в YC | Гостевая ВМ |
| --- | --- | --- |
| Имя | `dz10-pve` | `dz10-guest` |
| CPU | 4 vCPU, `standard-v3` | 1 vCPU, `qemu64` |
| RAM | 8 ГиБ | 2 ГиБ |
| Диски | HDD 30 ГиБ и HDD 20 ГиБ | VirtIO, 10 ГиБ |
| Сеть | `10.110.0.0/24`, публичный IPv4 | `10.111.0.10/24`, шлюз `10.111.0.1` |
| Доступ | разрешённые публичные `/32` | SSH через узел Proxmox |

Параметры и версии заданы в [config/lab.json](config/lab.json).
Гостевые диски размещаются на отдельном HDD. Облачный интерфейс
не включается в мост; гостевая сеть выходит наружу через NAT.
Отказоустойчивость одного узла не предусмотрена.

[Terraform YC](terraform/yc) и [Terraform Proxmox](terraform/proxmox) имеют
раздельные state. Установка Proxmox, подготовка сети, хранилища и реквизитов
доступа выполняются [сценариями настройки](provision) между двумя `apply`.
Провайдер `bpg/proxmox` использует HTTPS API, отдельную учётную запись
`terraform@pve` с токеном и штатный HTTPS без проверки сертификата.

Гость работает в программной эмуляции QEMU без KVM, существенно медленнее
аппаратной виртуализации. Terraform создаёт остановленного гостя, сценарий
задаёт `kvm=0` штатной командой `qm`, затем Terraform запускает ВМ.
Отдельного поля KVM в используемой версии провайдера нет.
Это учебный режим; его работоспособность на выбранном размещении подтверждается
облачным прогоном. Для аппаратного KVM нужен совместимый физический сервер
либо площадка с подтверждённой поддержкой вложенной виртуализации.

Пакеты Debian и Debian Security устанавливаются с `mirror.yandex.ru`.
Для Proxmox используется [зеркало Яндекса](https://mirror.yandex.ru/mirrors/download.proxmox.com/debian/pve/)
с проверкой подписанного индекса штатным ключом Proxmox. Доступные версии
компонентов закреплены в [config/proxmox-packages.json](config/proxmox-packages.json).
Публичный ключ репозитория включён в проект, его SHA256 проверяется перед установкой.

## Подготовка

Команды выполняются в PowerShell 7 из корня клона. Нужны Windows x64,
Git и [Python 3.12–3.14](https://www.python.org/downloads/windows/)
с командой `python` в PATH. Локальная установка Proxmox не требуется.

```powershell
git clone https://github.com/airiga1897/OTUS_DZ10.git
cd OTUS_DZ10
```

Файлы стенда находятся в ветке `proxmoxdz10`. До подготовки окружения
выберите ветку с файлами стенда:

```powershell
git branch --all
git switch 'ИМЯ_ВЕТКИ'
```

```powershell
python -m pip install --user poetry==2.4.1
./scripts/setup.ps1
```

Если `poetry` не найден, добавьте пользовательский каталог Python Scripts в PATH.
`setup.ps1 -Python 'ПУТЬ_К_PYTHON.EXE'` позволяет явно выбрать интерпретатор.
Окружение `.venv` устанавливается из `poetry.lock`; Terraform 1.13.5
и YC CLI 1.47.0 загружаются в `.tools` с проверкой SHA256. Повторный setup сохраняет настройки
и данные существующего стенда.

Используйте собственные облако и каталог с подключённым биллингом.
Оператору нужны `editor` на каталоге, `resource-manager.viewer`
и `quota-manager.viewer` на облаке. Эти права шире ресурсов ДЗ;
ограничение удаления собственным state и namespace реализовано в сценарии.

В `host.image_id` файла [config/lab.json](config/lab.json) закреплён официальный
образ `debian-13-v20261117` (`fd8ujnl2st97p9daufr1`) из семейства `debian-13`.
Доступность повторно проверяется
перед развёртыванием. Семейство образов не подменяет закреплённый ID.
Если потребуется другой образ Debian 13 x86_64 с cloud-init, после входа
получите сведения через [YC CLI](https://yandex.cloud/ru/docs/cli/quickstart)
и явно измените ID до создания стенда:

```powershell
./.tools/bin/yc.exe --config .local/yc/config.yaml compute image get-latest-from-family debian-13 --folder-id standard-images
```

Если образ отсутствует, подготовьте и загрузите собственный Debian 13
по [инструкции YC](https://yandex.cloud/ru/docs/compute/operations/image-create/upload).
Автоматическая замена ОС не выполняется. Гостевой образ закреплён URL
конкретной сборки и SHA512 из каталога Debian. Для его загрузки узлу нужен
HTTPS-доступ к `cloud.debian.org`; зеркало пакетов APT этот файл не заменяет.

### Вход через профиль YC CLI

Выполните однократный вход с собственным профилем этого клона:

```powershell
$env:YC_TRACE_LOG_PATH = 'NUL'
./.tools/bin/yc.exe --config .local/yc/config.yaml init
```

Следуйте подсказкам YC CLI: войдите в свою учётную запись и выберите облако
и каталог. Файл `.local/yc/config.yaml` содержит данные входа, исключён из Git
и доступен только текущему пользователю. Перед чтением сценарий проверяет
владельца и права файла. Профили других клонов не используются.

К командам `deploy`, `verify`, `destroy` добавляйте `--yc-profile`:
временный IAM-токен получается через `yc iam create-token` и передаётся
Terraform только в окружении дочернего процесса. Этот режим включается явно;
при неполном наборе переменных окружения автоматического перехода на файл нет.
Трассировка YC CLI отключается для операций с реквизитами.

В качестве альтернативы можно ввести реквизиты текущей сессии:

```powershell
. ./scripts/env.ps1
```

`env.ps1` запросит `YC_CLOUD_ID`, `YC_FOLDER_ID` и IAM-токен, полученный командой
`yc iam create-token`. Токен вводится скрыто и остаётся только в окружении.
После истечения токена повторите ввод. В этом варианте запускайте команды
управления без `--yc-profile`.

## Развёртывание и доступ

Перед первым запуском в своём облаке проверьте [config/lab.json](config/lab.json).
В `admin_cidrs` оставьте только собственные подтверждённые публичные IPv4 `/32`;
для одного текущего выхода можно задать пустой список `[]` — адрес определит
приватная функция YC. Список в конфигурации не заменяет проверку вашего маршрута.
После создания стенда разрешённые адреса дополняются, а размещение сохраняется.

```powershell
poetry run python scripts/lab.py deploy --yc-profile
```

Проверяются область ресурсов, размещение, образ, квоты и конфликты сетей.
Приватная Cloud Function создаётся до ВМ и вызывается по HTTPS с IAM-авторизацией.
IPv4 берётся из `requestContext.identity.sourceIp`; проверяются публичность адреса
и nonce запроса. Сторонние сервисы определения IP не используются.
Далее создаётся узел, устанавливается Proxmox с перезагрузкой на его ядро,
настраиваются сеть и хранилище, создаётся гостевая ВМ. Стенд остаётся работающим.

На всех длительных этапах выводятся начало, текущая операция и итог.
Во время ожидания сообщение обновляется каждые 30 секунд; оно не означает,
что операция уже завершилась. Реквизиты доступа и сырой вывод команд скрыты.
Установка и настройка выполняются отдельными заданиями `systemd` на узле,
независимо от SSH-сеанса. После временного разрыва клиент переподключается
и проверяет существующее задание. Повторный `deploy` подхватывает его при
совпадении входных файлов и параметров, без параллельного запуска установки.
Ожидание ограничено таймаутом; состояние и журналы сохраняются для повтора.

Порты 22 и 8006 доступны только разрешённым IPv4 `/32`.
Дополнительные разрешённые выходы SSH задаются явно в `admin_cidrs`.
Наблюдённые адреса хранятся отдельно; повторный `deploy` дополняет доступ,
сохраняя размещение. Планы с удалением или заменой ресурсов отклоняются.
При ошибке сохраняются state, контекст, ключи и данные восстановления;
после устранения причины повторите `deploy` либо выполните `destroy`.
Вывод ошибки удалённой настройки сохраняется в `.local/runtime/remote-error.log`.

При проблемах SSH проверьте маршрут, VPN, туннели роутера и разрешённые `/32`.
HTTPS до YC не подтверждает маршрут SSH. Стандартный порт SSH остаётся 22.

```powershell
poetry run python scripts/lab.py open
```

`open` сверяет локальные context/state, выводит размещение и URL вида
`https://ПУБЛИЧНЫЙ_IP:8006/` и завершается без облачной авторизации.
Используется штатный сертификат Proxmox. При первом открытии примите
предупреждение браузера для этого учебного стенда. Локальный CA не создаётся,
сертификаты на компьютер оператора не устанавливаются. Nginx не используется.
Terraform подключается по HTTPS с `insecure = true`: шифрование сохраняется,
проверка подлинности сертификата отключена по согласованному условию стенда.
Для просмотра предназначена учётная запись `reviewer@pve`. В форме входа
заполните поля раздельно:

| Поле | Значение |
| --- | --- |
| User name | `reviewer` (без `@pve`) |
| Realm (тип аутентификации) | выбрать `Proxmox VE authentication server` (`pve`) |
| Password | пароль из локального файла реквизитов |

Суффикс `@pve` в поле User name не добавляйте: Realm передаётся отдельно.
Полное имя `reviewer@pve` используется при обращении к API.
Скопируйте пароль в буфер обмена и вставьте в поле Password:

```powershell
(Get-Content .local/runtime/credentials.json -Raw | ConvertFrom-Json).ui_password | Set-Clipboard
```

### Подключение к гостевой ВМ по SSH извне

У гостя нет публичного адреса. Подключение идёт через публичный адрес узла
Proxmox по SSH на порту 22; выход оператора должен входить в разрешённые `/32`.
После успешного `deploy` выполните следующий блок в PowerShell 7 из корня клона.
Нужны команды OpenSSH `ssh` и `ssh-keygen`.

Адреса и имя пользователя берутся из контекста стенда. Используется ключ
оператора `.local/runtime/operator`, пароль не нужен. Ключи серверов закрепляются
по локальным ключам, переданным через cloud-init; проверка SSH-ключей не отключается:

```powershell
$labContext = Get-Content .local/runtime/context.json -Raw | ConvertFrom-Json
$hostIp = $labContext.host.public_ip
$guestIp = ($labContext.config.guest.address -split '/')[0]
$guestUser = $labContext.config.guest.username

$pveHostKey = ssh-keygen -y -f .local/runtime/pve-host
if ($LASTEXITCODE) { throw 'Не удалось прочитать SSH-ключ узла Proxmox.' }
$guestHostKey = ssh-keygen -y -f .local/runtime/guest-host
if ($LASTEXITCODE) { throw 'Не удалось прочитать SSH-ключ гостевой ВМ.' }
@("$hostIp $pveHostKey", "$guestIp $guestHostKey") |
    Set-Content -LiteralPath .local/runtime/manual-known-hosts -Encoding ascii

ssh -i .local/runtime/operator `
    -o IdentitiesOnly=yes `
    -o UserKnownHostsFile=.local/runtime/manual-known-hosts `
    -o StrictHostKeyChecking=yes `
    -o "ProxyCommand=ssh -i .local/runtime/operator -o IdentitiesOnly=yes -o UserKnownHostsFile=.local/runtime/manual-known-hosts -o StrictHostKeyChecking=yes -W %h:%p operator@$hostIp" `
    "${guestUser}@${guestIp}"
```

При исходной конфигурации откроется оболочка `student@dz10-guest`
на `10.111.0.10`. В гостевой Debian можно проверить систему и выйти:

```bash
hostname
cat /etc/os-release
exit
```

`ProxyCommand` передаёт SSH-соединение гостю через узел `operator@ПУБЛИЧНЫЙ_IP`.
Прямой проброс публичного порта на гостя не используется. Служебный файл
`manual-known-hosts` содержит только публичные ключи и удаляется вместе с runtime
при `destroy`. Приватные ключи и весь каталог `.local` остаются локальными.

## Проверка

Локальные проверки не создают облачные ресурсы:

```powershell
poetry run python scripts/check.py
```

Проверка работающего стенда:

```powershell
poetry run python scripts/lab.py verify --yc-profile
```

Проверяются HTTPS API и версия Proxmox, вход `reviewer@pve` и cookie-сеанс,
имя, CPU, RAM, диск, сеть и `kvm=0` через API,
SSH гостя с закреплённым ключом, завершение cloud-init, параметры внутри Debian
и отсутствие изменений в повторных Terraform-планах. Доступ к гостю идёт через
SSH-узел Proxmox. Ожидание гостя ограничено 30 минутами; состояния `running`
для успешного результата недостаточно.

| Требование | Реализация и проверка |
| --- | --- |
| Подключение к Proxmox | HTTPS API, токен, `insecure = true` |
| Создание ВМ | `proxmox_virtual_environment_vm.guest`, `apply` внутри `deploy` |
| Имя, CPU, RAM, диск, сеть | переменные из конфигурации; сверка API и гостевой ОС |
| Воспроизводимый запуск | раздельные state, lock-файлы, закреплённые образы и версии |
| Cloud-init, необязательная часть | пользователь, SSH, сеть, QEMU Guest Agent |

На Windows x64 с Python 3.14.2 пройдены 55 Python-тестов, 4 Terraform-теста
с подставными провайдерами, Ruff, `terraform fmt`, `validate` и проверка lock-файла
Poetry: [результаты локальных проверок](evidence/local-checks.json).
Также подтверждены подготовка из чистой копии и повторный `setup`:
[результаты подготовки](evidence/setup.json).
Функция `Remote.connect` покрыта на 100% по строкам и ветвям;
[отчёт измерения](evidence/ssh-connect-coverage.json) указывает область
проверки и команды воспроизведения. Это не покрытие всего проекта.
Функция подсказок `Lab.open` также покрыта на 100% по строкам и ветвям —
[отчёт](evidence/ui-open-coverage.json).
Вывод прогресса и восстановление после разрыва SSH проверены локальными
имитациями. Новый облачный прогон этих изменений не выполнялся.
Подтверждены два полных облачных цикла конфигурации со штатным HTTPS Proxmox:

| Цикл | Создание | Проверка | Удаление по state и API |
| --- | --- | --- | --- |
| [Первый](evidence/cloud-cycle-1.json) | успешно | успешно | подтверждено |
| [Второй](evidence/cloud-cycle-2.json) | успешно | успешно | подтверждено |

В обоих циклах проверены гостевая Debian 13, 1 vCPU, 2 ГиБ RAM,
VirtIO-диск 10 ГиБ, статическая сеть, `kvm=0`, завершение cloud-init,
SSH и отсутствие изменений в повторных Terraform-планах.
Вход учётной записи веб-интерфейса и cookie-сеанс проверены через HTTPS API;
отображение страниц браузера этими проверками не подтверждается.
После каждого цикла ресурсы удалены, окончательное удаление подтверждено
пустым Terraform state и API YC. Служебный каталог runtime очищен.
[Общий отчёт](evidence/cloud-cycles.json).

## Удаление

```powershell
poetry run python scripts/lab.py destroy --yc-profile
```

Удаляются гостевая ВМ, узел Proxmox, оба облачных диска, сеть, правила доступа
и Cloud Function. Данные ВМ теряются. Новое определение IPv4 не требуется.
Проверяется владение ресурсами; удаление подтверждается state и API.
Terraform использует закреплённые провайдеры из `.tools/provider-cache`,
подготовленные через `setup.ps1`, без повторного обращения к Registry.
Только после подтверждения очищается `.local/runtime`: state, ключи, токен,
планы и служебные журналы. При ошибке данные восстановления сохраняются.

Наблюдённые `/32` в `.local/observed-addresses.json` сохраняются с привязкой
к облаку и каталогу. Следующий `deploy` заново определяет текущий адрес.

Профиль входа не удаляется вместе со стендом, чтобы можно было повторить цикл.
После успешного `destroy` и завершения работы из корня клона можно полностью
удалить локальный профиль YC вместе с кэшем авторизации и журналами YC CLI:

```powershell
Remove-Item -LiteralPath .local/yc -Recurse -Force
Test-Path -LiteralPath .local/yc
```

Ожидаемый результат проверки — `False`. Удаляется только каталог профиля этого
клона; остальные данные в `.local` и глобальные профили YC CLI сохраняются.
Для следующего входа повторите `scripts/setup.ps1` и `yc init` с путём
`.local/yc/config.yaml`, как описано в разделе подготовки.
